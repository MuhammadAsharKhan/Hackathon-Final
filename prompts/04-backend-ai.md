# Prompt 04 - Backend AI assistant (run after 02 and 03)

Read prompts/hcm/00-SPEC.md completely (especially section 8), then knowledge.md, docs/ARCHITECTURE.md and the existing ai* files (aiKeyPool, aiProviders, aiSetup, ai controllers, AiKey and AiSettings models). Change server/ and docs only. Follow section 0 of the spec. Keep all AI code in ai* named files, mounted by one line in routes/index.js.

## Steps
1. Tool calling in the providers. Extend services/aiProviders.js so one call can carry tool definitions and return either text or tool calls. Gemini: send tools as [{ functionDeclarations: [...] }], read functionCall parts, answer with functionResponse parts. OpenAI-compatible (Groq, xAI): send tools as [{ type:"function", function:{ name, description, parameters } }], read message.tool_calls, answer with role "tool" messages that carry tool_call_id. Parameter schemas are plain JSON Schema objects. Keep the existing key rotation, cooldown, invalid-key and timeout handling: every model call in the loop goes through aiKeyPool so a failing key rotates to the next one.
2. services/aiAssistant.js: runChat({ user, message, conversation, now }) with the loop: build system prompt, call the model with the tools allowed for the user's role, execute each requested tool, feed results back, stop when the model returns text, at most 4 model calls and 15 seconds in total. Unknown tool or invalid arguments (validate with zod, clamp limits) are returned to the model as { error } so it can recover. A tool that throws returns { error: "unavailable" }. Role scoping exactly as spec section 8: build the tool list from the role and pass { user, employeeId } into every tool executor; the executors call analyticsService, leaveService, attendanceService and payrollService. Tool results contain no salary of any individual except get_my_last_payslip for the signed-in person. search_employees returns name, code, department, designation and status only.
3. Tools (name: arguments): get_headcount {departmentId?}, get_attendance_summary {from?, to?, departmentId?}, get_late_comers {from?, to?, limit?}, get_leave_summary {from?, to?, departmentId?} (include onLeaveToday with names and leave types), get_payroll_summary {month?} (totals and run status), search_employees {query, departmentId?}, get_my_leave_balance {year?}, get_my_attendance_summary {from?, to?}, get_my_last_payslip {}. Descriptions say plainly what each returns and that dates are YYYY-MM-DD. Department can also be given by name: resolve a departmentName argument to an id inside the executor (case-insensitive), and tell the model when it is not found.
4. System prompt builder (services/aiPrompts.js): today's date and weekday and the company timezone; the user's role and name; grounding rules ("answer only from tool results or the policy text, never invent numbers, say you do not know when the data is not available"); privacy rules ("never reveal another person's salary or any data your tools do not return, refuse politely and offer what you can do instead"); reply in the language the user used (English or Roman Urdu), short and direct; plus the POLICY TEXT generated by buildPolicyText(settings, leaveTypes): office start and grace time, late and half-day rules, weekend days, leave quotas and rules (working days only, overlap and balance errors, cancel rules), correction process, payroll formula and tax slabs, who can do what. The policy text must come from the live settings so answers change when Admin changes them.
5. Routes (spec section 5): POST /ai/chat (store the user and assistant messages in Conversation with an atomic push, cap stored messages and the history sent to the model at 20; reply includes toolsUsed and aiGenerated true), GET /ai/conversations/:id (own only), POST /ai/dashboard-summary, POST /ai/smart-leave.
6. Dashboard summary: the server builds the KPI JSON itself with dashboardService for the user's role and the given filters (never trust numbers from the client), asks the model for JSON { bullets: [3 to 5 short strings] } using only numbers in that KPI JSON, validates with zod and retries once. If it still fails or the model is down, return rule-based bullets built in code from the same KPIs with fallback true.
7. Smart leave: the prompt contains today's date and a calendar table for the next 35 days, one line per day: "YYYY-MM-DD Monday working" or "YYYY-MM-DD Saturday off" (weekends and holidays from settings), the leave types with codes, and these rules: "next Monday" means the first Monday strictly after today; ranges like "Monday and Tuesday" mean consecutive working days found in the table; wedding, family, personal -> casual; ill, fever, doctor -> sick; vacation, trip -> annual; no pay -> unpaid. The model returns only JSON { type, startDate, endDate, reason }. Validate with zod (type must be an existing code, ISO dates, start not after end), retry once, then run the real leave preview to add the working-day count and balance check, and return { type, startDate, endDate, reason, days, valid, problem?, aiGenerated }. On failure return { fallback: true } with 200. Nothing is saved.
8. Guardrails: one limiter for all AI routes, 20 requests per user per hour, answering 429 with a friendly JSON message; every request writes an AiLog (kind, message trimmed to 500 characters, toolsUsed, status, latencyMs); timeouts and provider failures return a friendly 503 message "The assistant is not available right now. Please try again in a minute." and never include provider text or keys. Messages must be 1 to 1000 characters.
9. Unit tests: buildPolicyText reflects changed settings; the smart-leave calendar table marks weekends and holidays correctly and starts tomorrow; the role to tool list mapping (employee gets only own-data tools, and no tool schema contains a salary parameter); zod validators for tool arguments and smart-leave output; the rule-based fallback bullets.
